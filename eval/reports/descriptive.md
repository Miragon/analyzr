# eval:descriptive

Generated by `pnpm eval:descriptive` (eval/tools/src/descriptive.ts); do not edit. M6 §3.11: how much of the LLM-free relation finding survives tool-style, descriptive models. Deterministic byte transforms of every scored landscape's models (`eval/tools/lib/descriptive.mjs`), cumulative, scored like `eval:candidates` against `expected.yaml`. Report only: no threshold. Element ids never change, so the ground truth applies unchanged.

**Variants**

| Variant | Transform |
|---|--:|
| baseline | the corpus models unchanged (executable Camunda 7 and 8) |
| engine-stripped | Camunda namespaces (camunda, zeebe, modeler) and everything in them removed, so no engine is detected; a C8 call target (zeebe:calledElement) moves verbatim to the standard BPMN attribute calledElement (the optimistic case: the tool keeps it) |
| descriptive | plus isExecutable="false"; call activities as collapsed subprocesses named exactly like the callee process (no call target; the exact name is the optimistic case); messages and signals without messageRef and signalRef (names only on labels), no bpmn:message and bpmn:signal definitions |
| pools | plus every message endpoint without a message flow in its file gets a message flow to or from a black-box pool per partner; every event, send and receive task stays what it is. Partners are the processes the rule tier pairs the endpoint with by message name in the unchanged models, each pool named exactly like the partner's pool or process (the optimistic case); without such a pair, one pool „Externer Partner“ |
| tasks | plus those endpoints' intermediate message throws and catches and send and receive tasks become plain tasks with the same message flows (a catch or receive task after an event-based gateway, and start, end and boundary events, stay events) |
| no-docs | plus every bpmn:documentation removed |

**Assumptions to verify** (tool behaviour the variants model; no real export has been checked yet, M6 §3.8):

- Descriptive tools (Signavio, ARIS, ADONIS, Bizagi, Visio exports) write no Camunda namespaces and no `modeler:executionPlatform`, so `engine` is null.
- A tool that keeps a call target writes the standard `calledElement` (engine-stripped); one that links a subprocess to another diagram exports a collapsed `bpmn:subProcess` named exactly like the linked process, without a call target (descriptive; the exact name is the optimistic case).
- Descriptive message and signal events carry no `messageRef` or `signalRef` and the tool writes no `bpmn:message` or `bpmn:signal`; the names exist only as labels.
- Modellers connect an exchange with another process by a message flow to a black-box pool named exactly like the partner (pools; the exact name is the optimistic case, and a partner the unchanged models do not reveal becomes one pool „Externer Partner“).
- Modellers draw such an exchange as a task (tasks); they keep message start, end and boundary events, and catches after an event-based gateway, as events.
- Message flows to black-box pools carry no name; the layout of added pools and flows is generated (pools below the diagram).
- Element ids survive the export unchanged (as the integrate skill requires, M6 §3.4); labels and documentation are the corpus texts.

**Facts v1 effects** (what the extractor and the rule tier make of the variants, not tool behaviour):

- engine-stripped copies a C8 FEEL call target (`=expr`) verbatim into `calledElement`. Without an engine, facts v1 treats only a JUEL expression there as dynamic, so such a call counts as a static target: an unresolved call instead of a dynamic one. The shift of unresolved-call and dynamic-call in engine-stripped is this facts gap, not tool behaviour; `descriptive.test.ts` pins it until a facts version fixes it.
- Facts v1 makes no relation endpoint of a collapsed subprocess (descriptive: no call relations left), of a task with a message flow (tasks: the message endpoints it converts are gone) or of a black-box pool.
- A message flow to a black-box pool answers its throw or catch: from pools on, no dangling-throw or unmatched-catch is computed for it, while candidates still pair it (only the exact pair a flow connects in one file is excluded).

**Claim size** is estimated per model as the server renders a relations task's input on a fresh import (`src/claim-estimate.ts`, pinned to `renderClaimInput` by the server test `claim-estimate.test.ts`): every candidate listed, without the judge-once lists `judged` and `skip`, which depend on the claim order; budget 100.0 KB. **Rule-tier precision** counts unlisted pairs as wrong (closed world). **Accepted under decision 24.2** counts the acceptances whose caller has an engine: the trust policy (S2c) turns the calls of engine-less models into proposals. Holdout numbers follow the holdout hygiene: none counts fewer than 5 items, and nested numbers differ by 0 or at least 5.
